# D3 Task: S02a authority and first shared store

27 September 2026. **Technical decision for review, not a ready Story.** This note narrows the first shared-store path in Pigboard's six ordered product outcomes. The [selected hosting design](hosted-fly-neon-free.md) and [delivery queue](../delivery-plan.md) now place the first hosted entry no later than S02a. The combined S02a preview exceeds the Story limit, so a complete prerequisite technical PR may increase the PR count. This note does not grant Jira access, provision a Fly app, or claim live gates passed.

## Outcome and evidence

S02a must let a connection administrator choose and later correct one Scubapig Jira project-and-board pair from named choices. The chosen pair must survive process restarts, be scoped to Pigboard, and never make a service-held credential or SQL password available to the caller. A denied human or agent must not list or change choices. S02a is the first user of the shared store, so the authority, root target, and correction guard cannot be postponed to S04.

The current code has an offline workflow-profile validator, a GitHub Projects adapter, and a standalone Cursor runner. It has no Pigboard HTTP service, caller authentication, Jira adapter, SQL store, or app role registry. The dedicated Pigboard Fly organization has no app. The Pigboard Neon Free project has an owner role and distinct root/child direct hostnames; owner-console SQL persistence and idle wake passed narrow probes. A scoped runtime SQL role, app-client TLS/reconnect, root/child denial, and service-identity Jira API metadata remain unproved. The Scubapig service account has no API credential; an earlier browser action to create one was rejected by automatic approval review pending a specific credential-scope and handling decision.

## Selected implementation path for review

1. **Start the Fly secret holder no later than S02a.** The first externally usable pair-selection command runs through one authenticated Pigboard service in the existing Fly organization. Fly runtime secrets hold the dedicated Neon runtime credential and the Scubapig Jira integration credential. A local CLI and an agent use the same service API. The normal CLI never connects to Neon or sends the Jira credential. The first host must have one source-controlled Machine configuration, a non-database-polling liveness check, bounded store wake/unavailable responses, authenticated command logging without secrets, restart/deploy verification, and a rollback path that does not revert a committed pair. Record the actual one-Machine spend against the selected estimate. S08 later adds automatic coordinator operation, load/second-teammate proof, quota observation and coordinator health; it does not introduce the first secret holder. These minimum first-host duties and S08's residual duties must be reflected in the reviewed design and queue before grooming.
2. **Use distinct revocable caller credentials for the one-team pilot.** Migration creates one uniquely keyed team-authority row on the pinned root before any credential exists. A named owner alone runs a migration-only bootstrap command against that root using the Neon owner credential. In one transaction it locks the row, verifies that no active owner grant exists, generates the next authority generation, and stores a high-entropy first human credential's one-way digest with a named human principal and owner plus connection-admin grants. It gives the plaintext to that owner once through a private local channel, never a repository or log. The normal CLI uses the owner's OS credential store. Only a current human owner may issue, rotate or revoke named human/agent credentials or approve a site/project candidate scope through a service admin command; it checks the owner grant inside the authority transaction. The owner may discover service-visible project names, then explicitly approve named project IDs; this approval does not select a board or activate work. A connection-admin agent may list and select a pair inside that approved scope but cannot issue or revoke any principal, grant itself owner status, widen project scope, or lock out the owner. The owner issues a separately named agent credential; the service returns its plaintext once over TLS, records only the agent's specific team/connection grant and generation, and the owner installs it in the agent's runtime secret store. Rotation records a new digest and revokes the old one atomically. If one-time delivery is lost or ambiguous, the owner revokes the uncertain credential by principal/issuance ID before issuing another. The sole owner's grant cannot be revoked through the normal service command; if that credential is lost, a named infrastructure custodian uses the migration-only recovery procedure: lock that same unique row, revoke the old owner, and issue one replacement in a single generation transaction. No standing unauthenticated app route exists. Every normal command checks the live-root principal, team, connection and current grant, with no cached permission. This is a pilot proposal, not browser sign-in or self-service invitation. A Jira service credential, workflow profile or Fly deploy grant gives no app role. The SQL credential is different: it is a privileged service secret, discussed below.
3. **Use a narrowly granted SQL role and a separate root pin.** A migration-only owner creates the minimum schema and `pigboard_app` login. The runtime role gets only required DML on its own tables, with no schema/role creation, restore or Neon API grant. Because that DML includes current grants and pair state, someone who steals the runtime SQL password can bypass the app role checks by writing directly; the service and its deploy custodian are trusted for that data. The SQL secret is never distributed to human/agent callers. A suspected leak stops administration and later effects until rotation and state audit. The direct production root hostname and database identity are reviewed non-secret configuration separate from the SQL secret; caller input cannot override them. The client uses direct TLS hostname verification. On startup and each reconnect it rejects a URL with a different host, pooler, database, or role before returning data. Before every pair read or write it checks its effective connection against the pin; a secret changed to the known child hostname must fail closed. A privileged custodian's endpoint reassociation under the same hostname remains outside the pre-S29 path, as the selected design already states.
4. **Keep the first records small and versioned.** Store named principals and current grants with an append-only generation event, one connection binding to the Scubapig Jira identity, an owner-approved site/project scope, and one selected `{projectId, boardId, version}` pair. The uniquely keyed team-authority row created by migration is the serialization point in the live root, including first/recovery bootstrap. Grant issue/revoke, approved-scope change, pair save/correction and later effect reservation all lock that row in their transaction, then re-read the current principal/grant generation, approved project, pair version and active-or-uncertain effect guard before writing. A pair change uses compare-and-swap on its expected version and commits the authority event/projection and pair together. If an effect reservation wins first, correction sees it and refuses; if correction wins first, the later reservation sees a stale pair version and refuses. A revocation that wins first denies the command; a command that commits first is recorded before revocation. A read-only choices command may fetch Jira metadata outside the transaction, then rechecks current grant/generation and approved scope under the root lock and projects the buffered names onto that current scope before disclosure. If revocation committed first, it returns no choices; if scope narrowed first, it removes now-unapproved choices. That final check is the read's authorization point; a later revocation does not retroactively cancel an in-flight authorized response. S02a starts with no effects but includes the explicit guard contract and concurrency fixture that later Stories must retain. Old trusted records retain their saved pair/version for inspection; no old version authorizes a new effect.
5. **Keep Jira metadata behind both the service identity and owner-approved project scope.** The first pilot scope is exactly the Scubapig site and PIG project ID `10001`, seeded by the owner in the versioned root authority record; board `2` is the intended first selection. The same owner-only scope command can add another project later by name and verified native ID, allowing the S02a project chooser to show every currently approved and service-readable project without a code deploy. An authorized connection administrator chooses a project from that intersection, then lists its associated boards that the integration identity can actually read. Selecting a board explicitly approves that one pair for the connection; no other board becomes active. A save revalidates the current approved project, native project/board association, and whether the board filter and columns can show the configured Task/To Do candidates; a mismatch names the decisive filter/column problem without saving. Record IDs plus names for clear output. If the service identity can read another Scubapig project or an unrelated board that the owner has not approved, neither human nor agent can list or select it. A normal pair-selection command or workflow profile cannot widen project scope. The D1 design and provisional S02a Story now say that owner-approved scope bounds the project list, the pilot begins with PIG, and the owner command is the path to broader customer choice. Live metadata proof and Story grooming remain open. To prove usable correction before accepting S02a, D1 must supply a safe second PIG board as a named live fixture; the existing Story's controlled metadata fixture remains useful for regression, but cannot alone establish the live operator journey. If no safe alternate is available, do not call live correction accepted. A missing or unreadable pair returns an actionable failure without saving. S02a does no issue-body read, Cursor request, Jira write, or automatic launch.

The other path considered was a pre-hosted local command with a Neon password and Jira token in each user's environment. It avoids an early Fly app but fails the selected service-held secret and current-grant boundary, and makes agent and human access depend on distributing powerful credentials. A second temporary secret service would add a new hosting component that S08 later replaces. The selected path uses the already chosen Fly component once.

## Contract and failure checks to prove before coding

- Verify a dedicated SQL runtime role can read/write only the Pigboard tables it needs and cannot create or alter authority schema. Test its direct-SQL reach honestly; DML on grants is trusted service authority, so possession of its password is treated as compromise. Do not use the owner role in the app.
- Verify direct root and child hostnames, the application's TLS hostname verification, rejection of a child-host secret, and reconnect after an observed Neon suspension with a bounded unavailable result.
- Verify one permitted human administrator and one permitted agent can list/save the same allowed pair; a named denied caller receives no choice data. Prove the unique authority row exists before first bootstrap and concurrent initial/recovery bootstrap cannot create two active owner grants. Prove one-time agent issuance, loss/rotation and revocation without leaked credentials. An agent must be denied owner issuance, grant escalation, peer revocation and owner lockout. Revoke a grant and prove the next command fails before Jira metadata access. Race list choices against revocation; a revoke committed before the final disclosure check must yield no names.
- Under the Scubapig integration identity, prove project/board metadata, association, filter and columns by API, including whether the board can show configured Task/To Do candidates. Make a controlled fixture where it can read an unrelated Scubapig project or board; listing and saving must still reject it until the owner approves that project. Race an owner scope reduction against list disclosure; buffered names outside the current scope must be removed. Supply a safe second PIG board fixture to prove live correction without activating it for normal work; align the Story's live and fixture QA wording before grooming. The signed-in human Jira UI is not service-identity evidence. Do not use or touch Safeguard Jira.
- Prove an invalid pair, stale version, ambiguous save response, and correction with active/uncertain effect fixture do not create an unreported selection. Race revocation against save and effect reservation against correction using the same root lock; accept only the transaction's serialized order. An unknown commit outcome must reconcile by reading the committed version, not blindly repeat a change.
- Verify that Fly deploy authority does not itself grant an API role, while documenting that a deploy custodian can technically read service-held secrets by deploying code. Verify the first-host restart, liveness, bounded failure and rollback path, and that runtime secrets never appear in logs, CLI output, profiles, or PR artifacts.

## Story-size audit before promotion

The complete S02a likely crosses six new code boundaries: hosted entry, caller credentials and grants, SQL schema/client/root pin, Jira metadata adapter, pair selection, and human/agent CLI. It also needs Fly packaging/configuration, behavior tests, and user/agent documentation. The current repository has no shared implementation for any of the first four. A preliminary file inventory is roughly 22–26 files even with focused modules: 2 package/dependency files; 2 Fly packaging/config files; 3 service/API/auth files; 3 SQL/schema/root-pin files; 2 Jira metadata files; 2 selection/CLI files; 4–6 behavior-test files; and 4–6 guide/contract/plan files. The number is an estimate, not a basis for hiding support files or claiming a two-day fit. It exceeds the 20-file limit before detailed planning.

**Consequence:** do not promote the present S02a preview or start coding it as one Story. After this authority design is reviewed and the SQL/Jira live gates are probed, re-groom a complete first technical outcome followed by pair selection, preserving the dependency order and all six product outcomes. That may require a seventh PR. A possible first outcome is “a named team administrator and scoped agent can authenticate to the Pigboard service and read their own current connection grant after a restart; revocation denies access.” It is only a candidate until its file/time count and independent plan review show a complete, usable technical outcome. The owner accepted six PRs as sufficient for the known split, not permission to exceed the standing per-Story limit.

## Author principle assessment

1. **Intuitive:** named pair choices remain the S02a human task; early hosting is invisible in normal use. The owner must handle one pilot credential during setup, with plain loss and rotation steps.
2. **Discoverable:** humans receive names and corrective errors; agents receive structured choices and denial codes. The guide must show bootstrap, one-time agent issuance and the current-role command before use.
3. **Delightful experience:** the saved pair avoids repeated Jira IDs and Fly hosts one shared path. The one-time owner bootstrap is extra setup but avoids distributing database or Jira secrets to every caller.
4. **Token saver:** a single scoped choices call and an explicit saved-version result avoid repeated metadata probes; errors must identify omissions without leaking denied choices.
5. **Secure:** the service holds provider/SQL secrets, serializes grant and pair changes from a migration-created authority row, restricts choices to approved scope, pins the live root, and rejects child hosts. A leaked runtime SQL password can directly alter grants, so secret custody and incident recovery are part of the first-host boundary; their live proof remains open.
6. **Agents are equal:** the same API accepts a distinct noninteractive agent principal with scoped connection-admin grant and structured results; issuance and rotation do not require the agent to use a human browser session.
7. **Dependable:** one root lock and version check order revoke, correction and later reservations; an ambiguous save reconciles by committed version. Host restart, credential loss, store wake and concurrency behavior still need tests before delivery.
