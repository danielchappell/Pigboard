# Check PIG Jira metadata with the service account

This is a pilot-only, read-only check for Scubapig project PIG (`10001`), Task (`10009`), board `2` and the PIG-only correction board `35`. It tests what the dedicated **Pigboard Jira Integration** service identity can read. It does not save a project-board pair, read an issue, prove an individual Pigboard caller's audience, or make S02a ready.

The command needs an Atlassian service-account OAuth client ID and secret. The dedicated credential has **not** yet been created or live-verified. Use only the authorized Scubapig organization and this dedicated account. Place the two values in separate absolute-path, owned mode-0600 regular files, each under an owned mode-0700 directory. Create and fill those files with a private editor or secret manager; do not paste values into a shell command, environment variable, prompt, ticket, review, or repository. Each value may have one final line feed, and no other whitespace. The command refuses unsafe files before contacting Atlassian.

```bash
npm run --silent jira:metadata -- --client-id-file /absolute/private/client-id --client-secret-file /absolute/private/client-secret
npm run --silent jira:metadata -- --client-id-file /absolute/private/client-id --client-secret-file /absolute/private/client-secret --format json
```

`--help` shows the same usage without credentials. Text and JSON report the token/identity check, each targeted route's HTTP status and local reason, selected native IDs and names, and what remains unproved. Exit `0` means only the targeted metadata reads and known PIG fixture checks completed. Exit `1` means authentication, access or metadata is incomplete. Exit `2` means invalid command usage or unsafe local credentials. An empty static board-project association is reported as `static_association_not_established`; it is neither a denied read nor proof that the pair is invalid. The command never prints the bearer, client values, raw filter query, vendor error body or unrelated board/project names.

For the currently targeted reads, the D1 service-read discovery derived this **19-scope read-only OAuth union** from Atlassian's [Jira platform API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/) and [Jira Software board API](https://developer.atlassian.com/cloud/jira/software/rest/api-group-board/):

`read:application-role:jira`, `read:avatar:jira`, `read:board-scope.admin:jira-software`, `read:board-scope:jira-software`, `read:filter:jira`, `read:group:jira`, `read:issue-details:jira`, `read:issue-status:jira`, `read:issue-type-hierarchy:jira`, `read:issue-type:jira`, `read:jql:jira`, `read:project-category:jira`, `read:project-role:jira`, `read:project-version:jira`, `read:project.component:jira`, `read:project.property:jira`, `read:project:jira`, `read:status:jira`, `read:user:jira`.

The list is for these metadata routes, not future issue or write operations. In particular, board configuration and static project association require the OAuth scopes `read:board-scope.admin:jira-software` and `read:project:jira`, while ordinary board listing uses `read:board-scope:jira-software` and `read:project:jira`. OAuth scope does **not** give the account Jira permission or board/filter visibility. A `403` on one route means to check that route's OAuth scope, the filter's sharing, and the account's PIG-local board/project permission before retrying. It is not a reason to grant global Jira administration. A `401` calls for checking the client credential; a wrong identity calls for using the dedicated service account. A `404` or missing known target may mean the board/filter is not visible to that identity. An unfinished page or malformed response is inconclusive; retry or inspect that route without treating absence as proof. Keep the account's effective access as narrow as the pilot allows.

The command makes no Jira writes or issue reads. Board 35 must still reference filter `10034` with the observed PIG-only query; a mismatch is incomplete without printing the query. Board 2's actual filter is read, but this command does not validate the full project-board relationship or issue membership. D1 still needs designated issue and contextual-permission reads, full filter/membership proof and a separate caller-audience rule before S02a/S02b live acceptance. Local fake-response tests prove only the command's behavior, not the service account's live access.
